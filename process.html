1. Plan and architectural evolution

Initial Conception vs. Final Architecture

Initial Scope: The project was initially conceived with basic multi-user authentication where users directly managed a global list of keywords.

Strategic Pivot: Real-world SEO rank tracking demands domain-level organization. We refactored the relational hierarchy to a 3-tier architecture: 1 User → Many Projects → Many Keywords → Daily Position History (30 Days).

Authentication

  • Secure Sign In & Log In
  • Bcrypt password hashing
  • Session auth & CSRF protection

Projects Dashboard

  • Project CRUD
  • Archived project view mode
  • Safe project deletion

Project Details & SEO

  • Add & edit keywords
  • 30-Day history generation
  • Today's simulated refresh
  • Position history table & charts

Metrics & Export

  • Total keywords metric
  • Top 3 best-ranked keywords
  • Best 7-day trend card
  • CSV Export
Key Architectural Decisions
  • Migration from Tailwind CSS to Clean Native CSS: Removed build-step complexity and bloated utility classes by adopting a handcrafted CSS design system with CSS custom properties (variables) for consistent theming and high performance.
  • Reusable Client-Side TablePaginator: Implemented a modular Vanilla JS class (TablePaginator) to handle client-side pagination, sorting, and live DOM rendering without third-party libraries.
  • Decoupling Seeder (M2) from Live Simulation (M3): Separated 30-day historical data generation (CLI/UI seeder in libraries/seeder.php) from the daily position update (ajax/refresh-positions.php), strictly enforcing one record per keyword per calendar day via UNIQUE(keyword_id, date).
What I Would Change in Hindsight

I would establish the exact database schema constraints (such as UNIQUE(keyword_id, date) and explicit SQL integer casting) right from the start. Transitioning from user-owned keywords to project-owned keywords midway required refactoring both backend queries and frontend JS state management simultaneously.

2. Prompts & Fixes

Case Study: UI Misinterpretation & Iterative Recovery (2 Fails → 1 Fix)
Keyword Statistics: From Inline Text Clutter to Reusable Stat Cards

The Core Challenge: Displaying aggregated keyword metrics (Total Keywords, Top Keywords, Best 30-Day Trend). This required 3 prompt iterations because the AI interpreted UI layout instructions literally rather than recognizing standard dashboard card components.

Iteration 1 (Failed UX): Stats Crammed Inside Dashboard Table Rows 
User Prompt:
Feature: Enhance the Projects table in the Dashboard to display rich keyword statistics directly underneath each project's name.

Instructions:
- Modify the project fetch logic (using subqueries, JOINs, or a secondary mapping loop) to append the following data to each project: Total Keywords - The exact count of keywords attached to the project; Top 5 Keywords - list (array or JSON) of up to 5 keywords with the best (lowest) current ranking position > 0; Best Trending Keyword - The keyword with the most positive trend in the last 30 days.
- Inject this enriched data into the window.__PROJECTS_DATA__ array for frontend rendering.
- When a completely new project is added via AJAX, ensure the JavaScript dynamically inserts the new project object with default values (Total Keywords: 0) so the renderer does not throw undefined errors."

AI Execution: The AI implemented batch subqueries in enrichProjectsWithStats(), but rendered a dense text block (.project-keyword-stats) directly inside the table cell under the project title (e.g. "Top: seo tools (#3) | Trending: rank tracker"). This overloaded the dashboard table and broke scannability.

Iteration 2 (Failed UI Format): Inline Text Header Next to Project Title 
User Prompt:
"UI Refactor: Move Project Keyword Metrics from Dashboard Table to Project Details Page

Remove the keyword summary metrics (total keywords, top 5 keywords, and best trend) from the main Dashboard projects table and move them to the Project Details page (Project.php).

Instructions:
- Clean up dashboard table
- Add summary metrics to project details header: display these metrics directly underneath the project name/header at the top of the Project Details view
- Aggregate these statistics in `Project.php` based on the project's current keywords and their position history
- Ensure these header summary metrics update dynamically via JavaScript whenever a keyword is added, edited, or deleted without requiring a full page refresh"

AI Mistake: While it successfully cleaned the dashboard and added ajax/get-project-stats.php, it literally inserted a group of inline <span> tags (.project-metrics) right next to the project title and status badge ("Project Name [Active] 9 keywords Top: seo tools (#3)") instead of building dedicated visual metric cards.

Iteration 3 (Resolved): Explicit Component Hierarchy & 3-Column Grid 
User Prompt:
"UI Refactor: convert project metrics into 3 summary stat cards (matching Dashboard style)

In `Project.php`, the keyword statistics are currently crammed as an inline text string next to the project title. Remove that text and place the metrics inside a 3-column grid of dedicated stat cards, identical in style to the summary cards on `Dashboard.php`.

Instructions:
- Remove the inline metadata text (9 keywords Top: ...) next to the project title and status badge.
- Create reusable `.display-cards` component for dashboard  and project pages
- Keep JS counters in sync with this unified markup when keywords or projects are added/edited/deleted."

Result & Solution: The AI removed the inline clutter and generated a unified 3-column .stat-grid with .stat-card elements (Total Keywords, Top Keyword, 30-Day Trending) sharing identical styles between `Dashboard.php` and `Project.php`, with dynamic client-side re-computation in updateProjectMetrics().

Root Cause & Key Takeaway:
  • Literal Prompt Traps: Phrases like "underneath the project name" cause the AI to attach DOM elements to the existing title container rather than designing a new visual layout section.
  • Design Language Precision: Specifying structural component terms ("3-column grid", ".stat-card component", "match Dashboard card pattern") eliminated ambiguity and produced clean, reusable CSS on the first try.
Prompt: First-Pass Success (Clean CSS Design System Migration)
Eliminating Utility Class Bloat with a Dedicated Semantic CSS Architecture

Context: The templates originally relied on cluttered, inline utility classes (Tailwind-style) that made PHP views hard to maintain and caused layout inconsistencies. The goal was to migrate to a bespoke, modular Vanilla CSS stylesheet (assets/styles.css) with a strict brand color palette.

User Prompt:
"Read the project specification and rules specified in AGENTS.md file. 

Refactor the styling across the application to move away from long utility class strings and use dedicated, clean vanilla CSS classes defined in a stylesheet (e.g., assets/css/styles.css or styles.css).

Design and color palette specifications:
1. Primary color: #5A2A27 - for main headers, primary CTA buttons, active states, active tab highlights, and key brand elements
2. Secondary color: #C4BBAF - for subtle card borders, background accents, table headers, and neutral hover states
3. Success / Confirm buttons: #16A34A / #15803D (Hover) — for "Save", "Create", "Confirm", and success badges
4. Danger / Delete buttons: #DC2626  / #B91C1C (Hover) — for "Delete", "Archive", 'Declined' trend and danger alerts
5. Backgrounds and text: Clean off-white/light-neutral background (#F9F8F6), white card containers, dark text (#1F2937) with high contrast and modern typography.

Instructions:
1. Define reusable CSS classes for all common UI components: buttons, cards, tables and pagination, modals and forms
2. Ensure the design is fully responsive, clean, and modern with smooth transitions (`transition: all 0.2s ease`)
3. Replace cluttered inline utility classes across `Dashboard.php`, `Project.php`, `Position.php`, and `header.php`/`footer.php` with the new semantic CSS classes."
Prompt: First-Pass Success (Reusable TablePaginator Component)
Decoupling Client-Side State with a Generic Vanilla JS TablePaginator Class

Context: As keyword and project counts grow, rendering large unstructured tables degrades performance and UX scannability. Instead of writing ad-hoc, duplicated pagination logic in separate view scripts, the objective was to implement an Object-Oriented, reusable client-side pagination engine (TablePaginator) with standard 10-item chunking, zero-indexed row counters, and dynamic search/filter reset.

User Prompt:
"Read the project specification and rules specified in AGENTS.md file. 

Create a generic, reusable JavaScript pagination helper class (`TablePaginator`) and implement it across all data tables in the application (Dashboard and Keyword Details page) with 10 items per page and row indexing.

Instructions:
1. Row Indexing: Add a # index column as the first column in the table header and body.
2. Pagination logic (10 items per page): Add a currentPage property (default 1) and pageSize = 10 to the JavaScript state object. eset currentPage = 1 whenever the user searches or changes the filter/sort criteria.
3. Pagination UI: Render pagination controls below the table - an info label ("page 1 of 45"), previous button (disabled on page 1), numbered page buttons (highlight the active page), next button (disabled on the last page); disable pagination controls when total items are less then 10 or no keywords are found 
4. Reusable Helper Class: Create the class to accept configuration options - tableBody (DOM element), paginationContainer(DOM element), pageSize(default 10), renderRow() (callback function returning the HTML string for a single ) ; provide public methods - setData() (sets new data, resets current page, re-render), goToPage() (navigated toa specific page), render() (calculates slices, draws rows, updates controls); handle empty datasets cleanly 
Ensure smooth integration with existing features. "

3. Retrospective

Key Learnings & What I Would Do Differently
  • Strict Baseline Milestone Discipline over Feature Creep: Early in the project, I became heavily focused on implementing extensive architectural features. Because of this deep dive into extra features, I only realized late in the cycle that the baseline brief required a strict separation between M2 (30-Day History Seeder) and M3 (Today's Live Position Simulation via AJAX). In hindsight, I would validate and lock in every mandatory milestone requirement first before expanding the scope with nice-to-have features.
  • Schema Constraints & Frozen Migrations Early: Enforcing database constraints early prevents messy data cleanup, deduplication scripts, and runtime SQLite migration pitfalls midway through development.
  • Early Uniform API & Data Contracts: Standardizing whether frontend AJAX endpoints communicate via raw JSON or FormData from day one eliminates unexpected 400 Bad Request responses and empty $_POST payloads.
  • Critical AI Supervision & Code Auditing: AI agents tend to create duplicate helper functions across different endpoints when tasked with incremental features. Actively reviewing, pruning, and consolidating duplicate methods keeps the codebase lean, DRY, and maintainable.
